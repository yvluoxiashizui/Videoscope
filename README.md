# Videoscope

面向长视频的内容理解平台。上传课程或讲座视频，自动完成语音转写、画面文字识别与结构化总结生成，并支持基于内容的追问。

## 能做什么

一次完整流程：注册登录 → 分片上传视频 → 提交分析 → 实时查看处理进度 → 获取结构化总结 → 就视频内容追问。

处理链路包含五步：从视频抽取音轨并按窗口切分，并发调用语音识别转成带时间戳的文本；按固定间隔抽取关键帧并识别画面文字；把语音与画面按时间轴融合成多模态上下文；交给大模型生成结构化总结；最后按内容切成检索块并向量化，供后续追问使用。

## 技术栈

Go / Gin / GORM / MySQL / Redis（Lua）/ RabbitMQ / 对象存储（S3 兼容）/ ffmpeg / 大模型与向量化服务（OpenAI 兼容接口）

## 关键设计

**上传与处理解耦。**分片合并落盘后，处理任务投递到消息队列异步执行，接口只做状态推进和消息投递。完整处理耗时以分钟计，接口响应在毫秒级。

**处理链路幂等。**同一视频可能被重复提交、消息可能重投。用三层防护：分布式锁按内容摘要互斥、消费前校验任务状态、状态推进走带条件的更新。

**多模态对齐不依赖识别服务。**语音识别接口不一定返回句子级时间戳，所以把音频切成固定长度分段，用分段边界作为时间轴刻度，配合同样粒度的上下文窗口完成对齐。

**分段转写并发执行。**音频分段彼此独立，串行处理时每段都要等一次网络往返。改成五路并发的 worker 池后，五分钟视频的转写耗时从约四分钟降到二十秒。并发数停在收益开始变平的位置，再高不会更快。

**结构化输出。**模型必须返回约定格式的 JSON，接口层强制 JSON 模式，解析前剥离可能存在的 Markdown 围栏。

**检索问答。**转写内容按语义切成块并向量化，追问时只召回最相关的几块拼成材料。相比把全文塞进提示词，成本随视频长度下降，而且减少了无关内容对模型的干扰。

**进度实时推送。**用 SSE 向客户端推送任务状态变化。轮询在长耗时任务期间会产生大量无效请求——绝大多数查询看到的状态都没变。

## 快速开始

依赖：MySQL、Redis、RabbitMQ、S3 兼容对象存储（如 MinIO）、ffmpeg。

```bash
# 初始化数据库
mysql -u root < mysql-setup.sql

# 配置（未配置 AI 服务时使用模拟实现，链路可完整跑通）
export VIDEOSCOPE_ASR_BASE_URL=...
export VIDEOSCOPE_ASR_API_KEY=...
export VIDEOSCOPE_LLM_BASE_URL=...
export VIDEOSCOPE_LLM_API_KEY=...

go run .
```

语音识别、大模型、向量化三个能力共用同一套 OpenAI 兼容接口配置，可分别指向不同服务商。未配置时自动退化为本地模拟实现，用于验证链路连通性。

服务默认监听 `:8080`。

## 接口

```
POST /api/register              注册
POST /api/login                 登录

POST /api/upload/chunk          上传分片
GET  /api/upload/status         查询上传进度
POST /api/upload/merge          合并分片

POST /api/analyze               提交分析
GET  /api/task/:id/events       订阅任务进度（SSE）
GET  /api/task/:id/download     获取视频下载地址
POST /api/task/:id/ask          就视频内容追问

GET  /healthz                   健康检查
```

**SSE 事件格式**

```
event: status
data: {"task_id":1,"status":2,"text":"处理中"}
```

状态码：0 待分析、1 排队中、2 处理中、3 已完成、4 处理失败。收到终态事件后服务端主动关闭连接。

**追问响应**

```json
{
  "answer": "视频在第 12 分钟讲解了……",
  "found": true,
  "sources": [
    {"start": 720, "end": 780, "content": "……"}
  ]
}
```

`sources` 给出答案依据的片段及时间范围，可据此定位到视频对应位置。
